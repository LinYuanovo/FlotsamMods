# Flotsam Mod 支持方案：调研 → 自研管理器 → 三个 Mod 实现方案

- 目标游戏：**Flotsam**（Pajama Llama Games，Steam AppID **821250**，2025-12-04 发布 1.0 正式版）
- 本地实测构建：**Unity 6000.3.16f1**，**Mono** 后端（非 IL2CPP），x86_64
- 本文所有技术结论均来自对本机 `Assembly-CSharp.dll`（4,327,424 B，3,624 个类型）的反编译与元数据核对，行号对应反编译产物 `_mod_recon/src/Assembly-CSharp.decompiled.cs`（300,874 行）
- 复现方式见附录 B

---

## 0. 结论速览（TL;DR）

| 问题 | 结论 |
|---|---|
| 有现成 mod 吗？ | **有 7 个**（Nexus Mods，2025-12-17 ~ 12-24 发布，均为 1.0 时代），但**没有任何一个**提供你要求的三个功能；且游戏**无官方 mod 支持**、**无 Steam 创意工坊** |
| 有通用框架吗？ | **推荐 BepInEx 5.4.23.5（Mono）+ HarmonyX**。官方明确"新 Unity Mono 游戏请用 BepInEx 5"，且 5.4.23.5 含 Unity 6 修复 |
| 为什么要自研管理器？ | BepInEx **只负责注入与加载**：没有清单、没有依赖解析、没有面向用户的启用/禁用/卸载、没有 mod UI。你要的"标准接口 + 自由增删"必须自研（`FlotsamModKit`） |
| 三个 Mod 可行性 | **全部可行，且不需要改游戏本体**。三个需求的关键 API 都已确认是 `public`（`World.RepositionTownheart` / `Community.PlayerCommunity` / `Producer.SetSelectedRecipe`），且 Mod 3 还有一个**原生预留、全程序集无人监听**的缺料行点击事件可用 |
| 最大风险 | Unity 6000.3 比 BepInEx 5.4.23.5 的 Unity 6 修复更新，**必须先做一次冒烟验证**；以及本机是"破解整合包"（含 Steam 模拟器），Steam 相关通道不可用 |

## 1. 现状与指纹（本机实测）

### 1.1 技术栈证据

| 事实 | 证据 |
|---|---|
| Unity 6000.3.16f1 | `Flotsam_Data/globalgamemanagers` 头部字符串 `6000.3.16f1` |
| **Mono 后端** | 存在 `MonoBleedingEdge/EmbedRuntime/mono-2.0-bdwgc.dll`（7.8 MB）；**不存在** `GameAssembly.dll` / `il2cpp_data` → 非 IL2CPP |
| 可反编译托管程序集 | `Flotsam_Data/Managed/Assembly-CSharp.dll` = 4.3 MB；另有 `Assembly-CSharp-firstpass.dll`（11 个类型） |
| 输入系统 = **Rewired** | `Rewired_Core.dll`（2.06 MB）、`Rewired_Windows.dll`、`Rewired_DirectInput.dll`；代码内 `FlotsamInputManager.RewiredPlayer = ReInput.players.GetPlayer(0)`（106758） |
| UI = UGUI + TextMeshPro + I2 Localization | `UnityEngine.UI.dll`、`Unity.TextMeshPro.dll`、`I2.Loc` 命名空间（287630 起）、`Assets/Code/GUI/**` |
| 数据驱动渠道 | `StreamingAssets/SurvivalGuide/**/*.json`（生存指南页面，373 B~3.4 KB/页）、`StreamingAssets/Maps/Custom.map`（自定义地图） |
| 游戏**不带**任何 mod 加载器 | 在整个 `Assembly-CSharp` 中检索 `BepInEx` / `MelonLoader` / `Harmony` / `MonoMod` / `IMod` → **0 命中** |
| 但游戏**自带** DevTools/秘籍系统 | `class DevTools`（37989）：`public static bool Unlocked { get; private set; }`（38001）、快捷键 `` ` ``（37995）、秘籍 `"iddqd"`（38009）、`Update` 门控 `if ((Unlocked \|\| Application.isEditor) && Input.GetKeyDown(_shortcut))`（38014） |

**推论（重要）**：既然游戏本体没有加载器，而 Nexus 上的 mod 文件只有 2~30 KB（典型的托管 DLL 补丁体量），且游戏里恰好有一个 `DevTools.Unlocked` 开关——那么 Nexus 的 "Dev Tools" mod 极可能就是"用外部加载器把 `DevTools.Unlocked` 置 true"。**该 mod 的加载器类型未能直接读取**（Nexus 页面被 Cloudflare 人机验证拦截，见 §2.6），需要你在浏览器里确认它的 Requirements 页。

### 1.2 本机副本的特殊性（影响通道选择）

- 这是**第三方整合包**：存在 `steam_api64.rne`、`steam_emu.ini`、`steam_api64.dll.backup*`、`免费申明.txt`、`防迷路ACG避难所.url`。
- 已存在**资源级改造**：`resources.assets.orig`（117 MB）与 `resources.assets`（117 MB）并存 → 中文汉化包直接改写了 Unity 资源文件；同目录还有 `Flotsam_汉化包/`（含 `工具_i2_patch.py`、`工具_unityfile.py`、`技术分析报告.md`、3,197 条 × 15 语言文本 CSV）。
- **后果**：① Steam 创意工坊/Steam DRM 相关通道不可用；② 任何"按文件哈希校验完整性"的 mod 管理器设计都必须**放弃哈希校验**（本机 `resources.assets` 与官方不一致）；③ 本地已有一套可用的**序列化文件读写工具**（`_l10n_work/unityfile.py` 是手写的 Unity 6 SerializedFile v22 读写器，因为本机 **未安装 UnityPy**）。

### 2.2 调研结果

**① Steam 创意工坊：不存在。**
抓取 `steamcommunity.com/app/821250/workshop/` 后，该 App Hub 的导航仅有 `All / Discussions / Screenshots / Artwork / Broadcasts / Videos / News / Guides / Reviews`——**没有 Workshop 项**。（检索时出现的 "FLOTSAM FRONT OFFICIAL" 是**另一款游戏**的创意工坊物品，与本作无关。）

**② 官方 mod 支持：没有。**
`Assembly-CSharp` 中检索 `BepInEx|MelonLoader|Harmony|MonoMod|ModLoader|IMod` → 0 命中；根目录也没有任何 `BepInEx/` 目录。官方仅提供**数据级**内容通道（生存指南 JSON、自定义地图文件）。

**③ Nexus Mods：有 7 个 mod，全部发布于 2025 年 12 月（1.0 正式版同期）。**

| # | 名称 | 作者 | 发布 | 下载 | 体积 | 功能 |
|---|---|---|---|---|---|---|
| 8 | QOL - Architect Pickup All | NarstyOtter | 2025-12-24 | 309 | 10 KB | 建筑师模式一键拾取全部已放置物 |
| 7 | Starting People Amount Customizer | NarstyOtter | 2025-12-23 | 288 | 3 KB | 自定义开局人数（1~10） |
| 6 | Quality of Life - Resource Bar | NarstyOtter | 2025-12-23 | 220 | 3 KB | 加宽顶部资源条 |

| 3 | More Names | angryPigeons | 2025-12-17 | 101 | 26 KB | 扩充海洋/码头/垃圾/诅咒船员名字池 |
| 2 | Give Item Menu | angryPigeons | 2025-12-17 | 578 | 14 KB | 游戏内刷物品菜单（搜索/分类/收藏/翻页/热键） |

**④ 对你三个需求的覆盖情况：0 覆盖。**

- 键盘移动（不打开地图走船）→ **无**
- 建筑快速查找/搜索 → **无**（`BuildablePanel` 原生只有"选中某建筑 → 按分类看同类"）
- 材料缺失 → 一键去生产 → **无**

**⑤ 其他框架：未发现 Flotsam 专用框架。** 检索 `Flotsam modding BepInEx Assembly-CSharp Harmony`、`Flotsam 1.0 modding framework` 等，命中的都是别的游戏（如 Streets of Rogue 的 BepInEx 指南、Ostranauts 的 BepInEx wiki），**没有** Flotsam 专属的 mod 框架或模板仓库。

### 2.3 结论

- **对"现成 mod"而言：没有可用方案。** 现有 7 个 mod 解决的是别的痛点，且它们与我们三个需求所需的游戏内部系统（`WorldMapTownheartPhycis2D` / `Community.CategorizedBuildables` / `Producer.Recipes`）完全不同。
- **对"通用框架"而言：有成熟方案**，但它只解决"代码注入 + Harmony 补丁加载"这一层，**不解决**你要的"管理器 + 标准接口 + 增删 mod"。因此：**用通用框架做地基，自研管理器做上层**（即第二步）。

### 2.4 通用 Unity Mod 框架对比

| 方案 | 支持 Mono / IL2CPP | 注入方式 | 补丁库 | 面向用户的管理能力 | 对 Unity 6 的适配 | 结论 |
|---|---|---|---|---|---|---|
| **BepInEx 5.4.23.5** | Mono（本作正是） | Doorstop 4.5（`winhttp.dll` 代理）+ 预加载器 | 内置 **HarmonyX**（`BepInEx/core/0Harmony.dll`） | ❌ 无清单/无依赖/无开关；`plugins/` 下所有 DLL 全加载 | ✅ 该版本明确含 *"Fix log writer errors for Unity 6"*，并把 Doorstop 升到 4.5.0 | ✅ **推荐** |
| BepInEx 6.0.0-pre.2 | Mono + IL2CPP | Doorstop 4 | HarmonyX | 同 5.x（更弱） | 面向 IL2CPP；**官方明说"要 mod 新的 Unity Mono 游戏请用 BepInEx 5"**，且**不兼容 BepInEx 5 插件** | ❌ 不选 |
| MelonLoader 0.6/0.7 | Mono + IL2CPP | 自注入 | HarmonyX | 有 `MelonPreferences`、mods 目录，但无成熟 mod 列表 UI | Mono 路线成熟度低于 BepInEx | ⭕ 备选 |
| UnityModManager (UMM) | 仅 Mono | 安装器改写游戏入口 | Harmony | ✅ **最接近你的诉求**：`Info.json` 清单、拖拽 zip 安装、UI 列表、启用/禁用开关（`OnToggle`） | ⚠️ 老项目，Unity 6 适配不确定；安装器侵入性大 | ⭕ 可借鉴其清单设计 |
| 自写 Doorstop 引导 | Mono | Doorstop | 自己接 Harmony | 全部自己写 | 完全可控 | ⭕ 仅在"不想引入第三方"时 |
| 直接改 `Assembly-CSharp.dll`（dnSpy/MonoMod） | Mono | 无 | 无 | 无 | 每次游戏更新即失效 | ❌ 拒绝 |

**推荐：BepInEx 5.4.23.5 作为"注入 + Harmony + 配置 + 日志"地基，在其上自研 `FlotsamModKit` 管理器**；清单格式借鉴 UMM 的 `Info.json` 思路，但语义按我们的生命周期重设计。

### 2.5 推荐的落地形态

```
Flotsam/                                  ← 游戏根目录
├─ winhttp.dll                            ← Doorstop 4.5（BepInEx 自带）
├─ doorstop_config.ini
├─ BepInEx/
│  ├─ core/                               ← BepInEx 5 运行时（含 0Harmony.dll）
│  ├─ config/BepInEx.cfg
│  └─ plugins/
│     └─ FlotsamModKit.Host.dll           ← 唯一由 BepInEx 加载的插件
└─ Mods/                                  ← 由 ModKit 管理（不是 BepInEx 管的）
   ├─ state.json                          ← 启用/禁用状态、顺序、依赖解析结果
   ├─ com.pajamallama.modkit.keyboardmove/{mod.json, KeyboardMove.dll, config.json}
   ├─ ...buildingfinder/{mod.json, ...}
   ├─ ...materialhelper/{mod.json, ...}
   └─ .trash/<id>-<timestamp>/            ← 卸载回收站（可回滚）
```

**为什么只让 BepInEx 加载一个插件**：BepInEx 的 `plugins/` 是"全加载"语义，无法表达启用/禁用/依赖；把生命周期收归 `ModKit.Host`，才能实现你的要求。禁用某个 mod = Host 不加载它 / 调用其 `OnDisable` 并回滚补丁，而不是靠 BepInEx。

### 2.6 未取到的证据（诚实声明）

- **Nexus 详情页被拦截**：用真实浏览器打开 `nexusmods.com/flotsam/mods/{2,4}` 时，Cloudflare 判定为人机验证（标题停留在"请稍候…"，`humanCheck.kind = "captcha"`）。因此 **7 个 mod 具体依赖哪个加载器（BepInEx 还是 UMM）、以及文件清单，未能核对**。列表页的元数据（名称/作者/日期/下载量/体积/简介）已成功读取。
  - **需要你做的事**：在浏览器里打开任一个 mod 页 → `Requirements` 一栏；确认后即可 100% 确定社区标准加载器。
  - 这**不影响**本方案：无论它们是 BepInEx 还是 UMM，我们的设计都是"BepInEx 地基 + 自研管理器"，而且自研管理器甚至可以把那 7 个 mod 当作"外来代码 mod"纳管（见 §3.9 兼容模式）。

## 3. 第二步：自研 Mod 管理器 `FlotsamModKit`

### 3.1 设计目标与非目标

**目标**
1. 预留**标准接口**，第三方 mod 只需引用一个小的 `Flotsam.ModKit.Abstractions.dll` 即可开发；
2. 支持**自由增删 mod**：安装 / 启用 / 禁用 / 卸载（含回滚回收站）；
3. 依赖解析与加载顺序；失败隔离（单个 mod 崩不影响游戏与其他 mod）；
4. 面向用户的**游戏内管理界面**（列表、开关、按键绑定、日志）；
5. 与 Unity/游戏**原生机制**集成：`GameEventDispatcher` 生命周期、`UIManager` 面板、Rewired 输入、I2 本地化、存档兼容。

**非目标（v1 明确不做）**
- 不做在线 mod 仓库/自动更新（后续可加）；
- 不做资源包（`resources.assets`）热替换——本机资源已被汉化包改写，且 Unity 资源替换本质上需要重启；v1 只做**代码 mod + 数据文件 mod**，资源 mod 标 `restartRequired: true`；
- 不改动游戏本体文件（只新增 `winhttp.dll`/`BepInEx`/`Mods`）。

### 3.2 分层架构

```
┌────────────────────────────────────────────────────────────────────┐
│ L4  ModKit.UI      游戏内管理界面（Mods/Keybinds/Log 三个页签）      │
├────────────────────────────────────────────────────────────────────┤
│ L3  Mods           KeyboardMove.dll / BuildingFinder.dll /          │
│                    MaterialHelper.dll …（只依赖 Abstractions）       │
├────────────────────────────────────────────────────────────────────┤
│ L2  Abstractions   IFlotsamMod / IModContext / 各 Service 接口       │
│                    + GameApi 门面（把游戏内部类型包一层，便于版本隔离）│
├────────────────────────────────────────────────────────────────────┤
│ L1  ModKit.Host    发现→校验→依赖排序→加载→生命周期→状态持久化→UI    │
│    (BepInEx 插件)   每 mod 一个 Harmony 实例；补丁登记与回滚          │
├────────────────────────────────────────────────────────────────────┤
│ L0  注入层         Doorstop 4.5 (winhttp.dll) → BepInEx 5 预加载器    │
└────────────────────────────────────────────────────────────────────┘
```

### 3.3 目录与清单规范

**mod.json（清单，随 mod 分发）**

```jsonc

  "id": "com.example.flotsam.keyboardmove",   // 全局唯一，反域名
  "name": "键盘移动 / Keyboard Move",
  "version": "1.0.0",                          // semver
  "author": "you",

  "entryAssembly": "KeyboardMove.dll",
  "entryType": "KeyboardMove.KeyboardMoveMod", // 实现 IFlotsamMod

  "permissions": ["harmony", "ui", "keybinds", "config", "save"],
  "keybinds": [
    { "id": "move.forward",     "default": "W",     "display": "前进" },
```

**state.json（管理器状态，用户数据）**

```jsonc
{
  "schemaVersion": 1,
  "mods": {
    "com.example.flotsam.keyboardmove": { "enabled": true, "installedAt": "2026-09-17T10:00:00Z" },
```

**配置（每个 mod 自己的）**：`Mods/<id>/config.json`，由 `IConfigService` 读写；**按键绑定单独存 `Mods/<id>/keybinds.json`**，避免与 Rewired 的 PlayerPrefs 冲突。

### 3.4 标准接口规范（`Flotsam.ModKit.Abstractions`）

```csharp
namespace Flotsam.ModKit.Abstractions
{
    /// 所有 mod 的唯一入口。生命周期严格成对调用（见 §3.5）。
    public interface IFlotsamMod
    {
        void OnLoad(IModContext ctx);   // 仅一次：注册补丁/服务/清单声明的按键
        void OnEnable();                // 可多次：应用补丁、订阅事件、创建 UI
        void OnDisable();               // 必须完全可逆：撤补丁、退订、销毁 UI
        void OnUnload();                // 释放非托管资源（程序集本身无法从内存卸载）
        void OnGameStart();             // GameEventType.GameStart
        void OnGameEnd();               // GameEventType.GameEnd（回主菜单/读档）
    }

    public interface IModContext
    {
        ModManifest     Manifest   { get; }
        string          ModDirectory { get; }
        IModLog         Log        { get; }
        IConfigService  Config     { get; }
        IKeybindService Keybinds   { get; }
        IPatchService   Patches    { get; }
        IGameEvents     Events     { get; }
        IUiService      Ui         { get; }
        ILocalizationService L10n  { get; }
        IModControl     Control    { get; }   // 自我禁用/请求卸载
    }

    public interface IPatchService           // 每 mod 独立 Harmony 实例，禁用即整体回滚
    {
        void Prefix   (MethodBase target, MethodInfo patch, int priority = 400);
        void Postfix  (MethodBase target, MethodInfo patch, int priority = 400);
        void Transpiler(MethodBase target, MethodInfo patch);
        int  RevokeAll();                    // 返回撤销的补丁数
    }

    public interface IKeybindService
    {
        IKeybind Register(string id, UnityEngine.KeyCode defaultKey,
                          string displayName = null, KeybindOptions options = default);
    }
    public interface IKeybind
    {
        string Id { get; }  KeyCode Key { get; set; }
        bool IsDown { get; }  bool IsHeld { get; }  bool IsUp { get; }
        bool Consume();                      // 边沿触发消费，避免多 mod 抢占
        event System.Action<KeyCode> Rebound;
    }

    public interface IGameEvents
```

### 3.5 生命周期与"启用/禁用/卸载"的真实语义

状态机：

```
Discovered → Validated → Loaded →(Enabled ⇄ Disabled) → Unloaded
                 ↘ Failed(reason)      ↘ PendingRestart
```

| 操作 | 实现 | 生效范围 |
|---|---|---|
| **安装** | 解压到 `Mods/<id>/`，校验 `mod.json`（schema/id/version/依赖/权限）→ 写 `state.json`（默认 `enabled: false`，让用户显式开启） | 立即出现在列表 |
| **启用** | 若 `type=asset` 或 `restartRequired` → 标记 `PendingRestart`；否则 `Assembly.LoadFrom`（首次）→ `OnEnable()` → Host 记录其补丁/订阅/UI 三张清单 | **多数 mod 立即生效**（无需重启游戏） |
| **禁用** | `OnDisable()` → `Patches.RevokeAll()`（`Harmony.UnpatchAll(modId)`）→ 释放事件订阅 → 销毁 UI/GameObject → 撤销注册的快捷键 | **行为立即回滚**；程序集仍驻留内存 |
| **卸载** | 先禁用 → `Mods/<id>/` 移入 `.trash/<id>-<时间戳>/`（可回滚）→ 询问是否连 `config.json`/`keybinds.json` 一并删除 → 释放该 mod 占用的 `PanelID`/热键 | 文件立即移除；内存与资源 mod 需重启 |

**必须诚实说明的边界（Mono 的硬限制）**：Unity 的 Mono 运行时**无法卸载已加载的程序集**（没有 .NET Core 的 `AssemblyLoadContext` 卸载能力）。所以"卸载"的语义是：**文件删除 + 行为回滚**；要彻底释放内存（以及资源类改动）需**重启游戏**。管理器会在 UI 上把需要重启的操作标成 `⟳ 重启后完全生效`，而不是假装热卸载成功。

**故障隔离**：每个 mod 的 `OnLoad/OnEnable` 用 try/catch 包裹并记日志；失败即 `Failed(reason)`，UI 上显示红色徽标 + 详情，**不阻断**游戏或其他 mod。补丁在 `Harmony.Patch` 阶段失败同样按此处理。

- **不校验文件哈希**：本机 `resources.assets` 已被汉化包替换，任何完整性校验都会误报。

### 4.1 Mod 1：键盘移动（不打开地图即可驾驶）

#### 现状与根因（已定位到确切机制）

游戏里"船"= **镇心（Townheart）**，驾驶逻辑只在**世界地图视图**里跑：

| 环节 | 符号 | 行号 | 说明 |
|---|---|---|---|
| 输入汇聚 | `FlotsamInputManager.GetMovementInput(rewiredAction rotateLeft, rotateRight, backward, forward)` | 107211 | 返回 `Vector2(-left+right, -back+forward)`；相机驱动镇的开关打开时再叠加地图相机输入 |

| 物理 | `WorldMapTownheartPhycis2D.ApplyMovementAndRotation(float,float)` → `MovePositionAndRotation` / `SetVelocity` / `AddForceAndTorque` | 164058 / 164078 / 164085 / 164091 | `Rigidbody2D.MovePosition`，用 `Time.fixedUnscaledDeltaTime` |

#### 交互设计

- 地图**关闭**时：`W/S` 前进后退、`A/D` 旋转（默认取游戏现有绑定，可改键），速度/转向跟地图里一致；
- 地图**打开**时：原生逻辑接管（我们的驱动自动让位）；
- 可配置：速度倍率（默认 1.0，忠于原味）、是否消耗引擎能量（默认消耗）、"按住才走 / 切换式"模式；
- 冲突保护：打字中（`UIState.Typing`）、暂停中（`GameManager.Gamepaused`）、面板声明 `PanelContainerFlags.BlockCameraInput`（76417）时**不驱动**。

#### 实现方案（推荐：世界视图驱动器，走原生提交路径）

```csharp
internal sealed class TownheartKeyboardDriver : MonoBehaviour
{
    private IKeybind _fwd, _back, _left, _right;

    private void FixedUpdate()
    {
        var um = GameManager.UIManager;
        if (um == null || GameManager.Gamepaused) return;
        if (um.UIState == UIState.Typing) return;
        if (UIManager.HasFlagsSet(PanelContainerFlags.BlockCameraInput)) return;

        var map = GameManager.WorldMapManager?.WorldMap;
        if (map == null || map.isActiveAndEnabled) return;      // 地图开着 → 交给原生
        if (map.IsTownMovementBlocked) return;                   // 159648

        float fwd = (_fwd.IsHeld ? 1f : 0f) - (_back.IsHeld ? 1f : 0f);
        float rot = (_right.IsHeld ? 1f : 0f) - (_left.IsHeld ? 1f : 0f);
        if (Mathf.Approximately(fwd, 0f) && Mathf.Approximately(rot, 0f)) return;

        var world = GameManager.WorldManager.World;              // 权威世界状态
        Vector3 fromPos = world.TownheartWorldPosition;          // 156535
        Quaternion fromRot = world.TownheartRotation;            // 156541

        float dt       = Time.fixedUnscaledDeltaTime;            // 与原生一致（164060/164072）
        float rotDelta = rot * map.RotationSpeed * dt;           // map.RotationSpeed (159658)
        Quaternion toRot = fromRot * Quaternion.Euler(0f, 0f, -rotDelta);

        float dist  = fwd * map.MovementSpeed * dt;              // map.MovementSpeed (159656，已含引擎倍率)
        dist = EngineApi.Throttle(world, dist);                  // 复刻 Engine.ReturnMoveableDistance (22364)
        Vector3 toPos = fromPos + (toRot * Vector3.up) * dist;    // 镇心始终沿自身 up 前进

        if (dist == 0f && Mathf.Approximately(rotDelta, 0f)) return;

        // 走原生提交链路：与 WorldMap.Deactivate(159734) 完全同一条路
        MovementEvent.DispatchTownheartMove(fromPos, toPos, fromRot, toRot, Mathf.Abs(dist));
        EngineApi.ConsumeEnergy(world, Mathf.Abs(dist));          // 159769 同款能耗
    }
}
```

要点：

1. **绝不自己写 `World.TownheartWorldPosition`**（它是 `private set`，156535）——必须经 `MovementEvent.DispatchTownheartMove`（40865）/`World.RepositionTownheart`（156616），这样瓦片（`tile.RepositionTownheart`，156630）、代理人、地标事件才会一起正确更新。
2. **让位给原生**：`map.isActiveAndEnabled` 为真即直接 return，避免双重积分。
3. **不要重新激活地图**：会破坏暂停时的全局物理驱动（见上表"暂停特例"）。
4. **能耗与引擎节流**：用 `Buildable.TryReturnBuildableExtendable<Engine>(out engine)`（`Engine` 22127，`ReturnMovementSpeed` 22359，`ReturnMoveableDistance` 22364）拿到镇心的引擎；若拿不到就退化为"按 `WorldMap.MovementSpeed` 走、不额外节流"，并在 UI 上标注。
5. **驳回的方案（记录原因）**：为了省事去 patch `WorldMapManager.Initialize` 让它不 `SetActive(false)`（162441）——暂停时 `WorldMapTownheartPhycis2D.Update` 会驱动 `Physics2D.Simulate`（163952-163958），等于全局物理被解锁，会造成世界冻结失效。

#### 按键自定义绑定

- 默认值：从游戏当前绑定反查（`GetFirstKeyboardMapWithAction(69..72)`，107023），所以"原生改了键，mod 跟着变"；
- 覆盖值：`IKeybindService` 的 `Mods/<id>/keybinds.json`，用 Rewired 键盘轮询 `GetKey(KeyCode)`——**不依赖 `Input_Category_Map` 是否启用**，这是"地图关着也能读到按键"的技术前提；
- UI：管理器 `Keybinds` 页签 + mod 自己的小面板；
- 冲突：与原生动作同键时给黄标提示（读 `GetButtonKeyCodeString`，107256）。

| 风险 | 缓解 |

### 4.2 Mod 2：建筑快速查找（右侧按钮 + 分类 + 搜索）

#### 现状与根因（"材料不足"的判定点已找到确切代码）

生产（Workshop 类 `Producer`）的面板里，每个配方行由 `RecipeDisplay.UpdateDisplay()` 刷新，**"材料不足"就是这一句**：

```csharp

{

                   have < ingredient.Amount,                                        // 70845 ← 不足
```

权威判定（真正决定能不能开工）在 `Producer.TryReserveRequiredItems(...)`（25368）：

```csharp

{ recipe.AddMallfunction(GameManager.Settings.BuildableSettings.ErrorItemsMissingProperties); // 25388
  return false; }
reservedItems = ResourceManager.ReserveClosestItems(base.Buildable, recipe.Ingredients);        // 25391
```

**"哪个建筑能产这个材料"游戏自己就有判定**，而且有三层（从精确到宽泛）：

```csharp

// ② 生产者级："我（这个 Producer）做这个配方吗"（Producer.IsProducerOf，25701）

// ③ 场景条件里的等价写法（147864 / 26383）
```

**已放置生产者有现成注册表**（比遍历全部建筑更好用）：

| 符号 | 行 | 说明 |
|---|---|---|
| `Community.PlayerCommunity.Producers`（`List<IItemProducer>`） | **7320** | 所有**已放置**生产者的活注册表；由 `Community.AddProducer(IItemProducer)`（8081）/`RemoveProducer`（8093）维护，`Producer.Initialize`（24960）/`Remove`（25065）调用 |
| `interface IItemProducer` | 95867 | 仅 4 个成员：`Buildable`(95869)、`List<ItemProperties> ProducedItems`(95871)、`ExportResourceProvider`(95873)、`GetItemsInProductionCount`(95875) |
| `Producer.ReturnProducesItem(ItemProperties)` | **25788** → 26428 | 精确判定"该生产者能产此物品" |
| `Producer.ProductionProperties.Recipes`（`List<ProductionRecipeProperties>`） | 24848 + **26234** | 该建筑的全部配方；`ProductionRecipeProperties.RequiredItems`(26329) / `ProducedItems`(26339) |

**"打开某建筑的生产菜单"**：`Buildable.OnSelected(true)`（17237）→ `GameManager.UIManager.DisplayPanel(this)`（17240，因为 `Buildable : IPanelContext` 且 `PanelID => PanelID.BuildablePanel`，15949）→ `BuildablePanel` 激活元素 → `ProductionPanel.Activate`（69463）在 `buildable.TryReturnBuildableExtendable<Producer>(out _producer) && _producer.ProductionProperties.Type == Producer.Type.Workshop`（69466）时显示。

**"安排生产"**：`Producer.SetSelectedRecipe(int)`（**public**，25098）→ `Producer.IncreaseSelectedRecipeAmountToProduce()`（**public**，25210，唯一"加量 + 入队"的公开路径，内部会调私有 `TryQueueRecipe` 25182 → `QueueRecipe` 25155）。之后 `GameManager.LateUpdate`（**107545**）每帧泵动 `Producer.UpdateQueuedProducer()`（25304），材料到货即**自动**预留开工——**不需要我们自己写重试循环**。

> 注意：`Producer.AddRecipe(int)`（25087）虽然 public，但**不用我们自己调**——`Producer.Initialize`（24956-24959）已经为每个配方建好 `Recipe` 实例。`Recipe.IncreaseAmountToProduce(int)`（24611）只改计数器、**不入队**。

#### 交互设计（关键发现：原生行已经预留了点击事件，且**全程序集无人监听**）

缺料行 `RecipeItemDisplay` 本身就是 `IPointerClickHandler`，并公开了两个 `UnityEvent`：

```csharp
// RecipeItemDisplay  (70891)
public UnityEvent OnLeftClickEvent;    // 70923
public UnityEvent OnRightClickEvent;   // 70926
public void OnPointerClick(PointerEventData e) { ... left → OnLeftClickEvent.Invoke() (71043)
                                                 ... right → OnRightClickEvent.Invoke() (71047) }
public ItemProperties ItemProperties { get; }   // 70941
public Producer.Recipe Recipe { get; }          // 70939
```

全文件检索 `OnLeftClickEvent.AddListener` / `OnRightClickEvent.AddListener` → **0 命中**（只有 71043/71047 的 `Invoke()` 与 71058/71059 的 `RemoveAllListeners()`）。也就是说：**"点缺料行 → 去做这件事"的交互入口游戏已经留好了，只是没用**。这让本 mod 可以做到"零新增控件"。

- **默认交互**：**左键点击缺料的那一行** → 自动找到能产该材料的建筑（相机飞过去 + 打开其生产菜单 + 选中配方 + 数量 +1）；`Alt+左键` = 填满队列；`Shift+左键` = 连续生产。
- **可视化提示（可选，默认开）**：patch `RecipeDisplay.UpdateDisplay`（70836）后给缺料行加一个小箭头角标 + 悬停提示"由 <建筑名> 生产（距离 X）；材料 3/5，缺 2"。**不改变原生布局结构**（只在行内加子物体）。
- 找不到生产者（没有已完工的 Workshop 生产者能做该物品）→ 不响应点击 + 提示原因；产能上限（`IsProductionLimitReached`，**109339**）命中 → 明确提示而不是静默失败。
- 递归提示：若该材料自己的配方原料也缺，提示"上游还缺 X"（可选，深度 1~2）。
- **适用边界**：**仅 Workshop 类生产者**。农场（`Producer.Type.Farm`）走 `FarmPanel`，其 `Initialize(..., itemDisabled: false, ...)`（68788）**硬编码不高亮缺料**，且缺料故障的挂载点在 25388 明确以 `_properties.Type == Type.Workshop` 为条件——所以农场没有可挂的缺料行，v1 不支持农场。

**第 1 步：挂上"缺料行点击"（主路径，零新增控件）**

```csharp
// RecipeItemDisplay 行由 ChildBehaviourCache 池化复用（70763 / 70841），
// 所以要对"每个行实例"只订阅一次：用 HashSet 或给行对象挂一个标记组件。
void OnRowCreated(RecipeItemDisplay row)
{

        row.OnLeftClickEvent.AddListener(() => GoProduce(row.ItemProperties, row.Recipe, Multiplier()));
```

`RecipeDisplay.UpdateDisplay`（70836）会因 `InventoryUpdatedEvent`（70785/70871）频繁刷新行内容，但**行实例是复用的**，故只需按实例订阅一次。
若还需要"角标 + 悬停提示"，再用 `IPatchService.Postfix(RecipeDisplay.UpdateDisplay)`（70836）在刷新后给 `have < amount` 的行加子物体（幂等："存在即复用"）。

**第 2 步：解析"谁能产这个材料"（用游戏自己的注册表）**

```csharp
static Producer FindProducerFor(ItemProperties item, out Buildable owner)
{
    owner = null; Producer best = null; float bestD = float.MaxValue;
    Vector3 here = CameraController.Instance ? CameraController.Instance.ReturnFocusPoint() : Vector3.zero;

    foreach (IItemProducer ip in Community.PlayerCommunity.Producers)   // 7320：已放置生产者注册表
    {
        if (ip is not Producer p) continue;
        Buildable b = ip.Buildable;                                    // 95869
        if (b == null || b.BuildPhase != BuildPhase.Finished) continue; // 15884
        if (!p.IsEnabled()) continue;
        if (p.ProductionProperties.Type != Producer.Type.Workshop) continue;  // 与 69466 同款过滤
        if (!p.ReturnProducesItem(item)) continue;                      // 25788 → 26428（精确）
        float d = (b.transform.position - here).sqrMagnitude;
        if (d < bestD) { bestD = d; best = p; owner = b; }
    }
    return best;
}
```

**第 3 步：打开它的生产菜单**

**第 4 步：安排生产（只用公开 API）**

```csharp

                 .FindIndex(r => r.ReturnProducesItem(item));   // 26428
```

**为什么"缺料也能排、且以后会自动开工"**：`QueueRecipe`（25155）在材料不足时经 `TryReserveRequiredItems`（25368，判定 25386）**干净地返回 false**，而 `GameManager.LateUpdate`（107545）每帧泵 `Producer.UpdateQueuedProducer()`（25304）→ `TryQueueRecipe()`（25182），所以材料一到位就自动预留、派工、生产。**我们不需要写任何重试轮询。**

**第 5 步：构建/升级路径（同一需求的第二入口，建议一并支持）**：建造或升级缺材料时，判定是 `ResourceManager.AreCommunityResourcesAvailable(requiredResources)`（**109215**），需求来自 `Properties.RequiredResources` / `Properties.UpgradeResources`（16591/16647），提示文案 `ErrorItemsMissingProperties`（142410）。在这一侧也放同一个入口，复用第 2~4 步。
6. **安全**：所有调用都在主线程（`Update`/UI 回调内）；`OnDisable` 时移除所有按钮并撤销 patch（`IPatchService` 自动做）。

### 4.4 Mod 4：可缩放小地图（新增需求）

#### 三条候选路线与取舍（基于 recon 的硬证据）

| 路线 | 做法 | 为什么选 / 不选 |
|---|---|---|
| A. 第二相机 + RenderTexture + RawImage | 复制 `CameraController.Instance.Camera` 配置 → 俯视渲染 → RT 贴到 RawImage（RT→RawImage 本作已有先例：48535 `new RenderTexture(1024,1024,24,GraphicsFormat.R8G8B8A8_UNorm)` → 48538 `_portrait.texture = renderTexture`） | ❌ **不选**：① 世界相机是**透视**（`CameraPresetProperties.FOV = 60f`，35204），缩放是沿 `_zoomTransform` 的物理距离而非 `orthographicSize`；② 项目**已在用 URP 相机堆叠**（`_data.cameraStack.AddUnique(_overlayCamera)`，35063），再加一台 Base 相机渲染到 RT 有管线冲突风险；③ `cullingMask`/层级是**场景序列化数据**，全文件只有一处 cullingMask 运算（水面反射相机 165593），代码层无法确定该屏蔽哪些层 |
| B. 程序化 Texture2D（数据驱动绘制）✅ **采用** | 从 `WorldManager.ReturnWorldBounds()` / `World.Tiles[].WorldBounds` / `ISpawner` 标记 / `ScoutingState` 画一张贴图，贴到 RawImage | ✅ 数据源全是 **public**，免疫渲染管线与层级不确定性；`Texture2D.SetPixels32 + Apply` → RawImage 在本作也有先例（238409-238479）；不新增相机，零渲染副作用 |

#### 绘制与交互

- **投影**：`scale = size / max(bounds.w, bounds.h) * zoom`；`WorldToPx(w) = size/2 + (w - center) * scale`（top-down 空间 = `(x, z)`）。
- **绘制顺序**：背景 → 逐瓦片海域填充 + 描边 → 标记（按 `ScoutingState` 四色：未知灰 / 传闻浅灰 / 已确认黄 / 已侦察绿；垃圾橙；地标 2px、POI 1px）→ 镇心 6×6 蓝块 + 朝向刻线。
- **自由缩放**：滚轮以**光标所指世界点为锚**——先记录光标下的世界点，缩放后反解，把差值补回 `center`，因此缩放不跑偏：

```csharp
if (!CursorWorld(e, out var before)) { ZoomBy(f); return; }
ZoomBy(f);
if (CursorWorld(e, out var after)) _center += before - after;   // 锚定补偿
```

- **平移**：拖拽时用 `ScreenPointToLocalPointInRectangle` 求当前/上一帧局部点，`center -= (now - prev) / scale`；拖拽自动关闭"跟随镇心"。
- **双击**：把该点设为地图中心。「适应世界」= `zoom = 1` 且 `center = bounds.center`。
- **刷新**：默认 6 Hz（可配），仅窗口可见时重绘。
- **纹理**：`new Texture2D(320, 320, TextureFormat.RGBA32, false)`，`FilterMode.Point`，`Color32[]` + `SetPixels32` + `Apply(false)`；禁用时销毁。

## 6. v2 修复记录：首轮实测的四个问题与根因

首轮交付后用户实测四个模组"效果都不好"。四个问题都指向我在 §4 里的**错误假设**，以下是根因与重做方案（全部有代码证据）。

### 6.1 键盘移动：不生效，且其他建筑视角错乱

用户反馈：**没有真实移动**，反而"其他建筑视角乱了"。

**两个根因**（都是致命的设计错误）：

1. **`MovementEvent.DispatchTownheartMove` 不是"移动原语"**。它的**唯一**监听者是 `World.OnTownheartMove`（156673/156676），一次派发会：
   - `WorldTile.RepositionTownheart`（157766）→ `ClearSpawners()` 并把每块瓦片的地标/兴趣点/道路**全部反注册再重新生成**（157768-157787）；
   - 连带 `GameEventType.UpdateAllObstacles`（157773）→ 清空寻路多边形/图（120382-120393）；
   - `TerrainManager.OnTownheartMoved`（110358-110372）→ **整块地形/区域网格双重循环重建**；
   - `UnityNavMeshNavigator.OnTownheartMoved`（115967-115971）→ 把**每个漂流者 warp** 到缓存的导航网格位置；
   - `MooringPoint` 每次派发排一条寻路查询（23721）。
   我把它放在 `FixedUpdate` 里每帧调用（约 30 次/秒）→ 持续重生成 + 反复 warp = "视角乱了"。
   另外 `GameEvent.Dispatch` 会吞掉监听器异常（40422-40436），所以一旦某个监听者抛异常，剩下的就不再重锚定 → 画面"部分错位"。

2. **`World.RepositionTownheart` 只接受"已生成瓦片范围内"的位置**（156618 → `IsPositionInWorldBounds` 157083），越界时只记一条 `LogException` 并 `return false`（156636）。而**瓦片只由 `WorldMap.LateUpdate`（159786）生成**——地图关着时它根本不跑，瓦片列表永不增长 → 远航在瓦片边界被静默拒绝 = "没有真实移动"。

3. 附带修正：方向向量算错了。地图移动器是 2D 的，对外暴露的朝向是 **Y 轴**旋转（`Rotation => Quaternion.Euler(0, -rb.rotation, 0)`，163889），2D "up" 对应世界 **+Z**（`Vector2TopDown = (x,z)`，205071）。我写成了 `toRot * Vector3.up`——而 `Vector3.up` 在 Y 轴旋转下**不变**，等于把船往天上开。正确是 `toRot * Vector3.forward`。

**v2 方案：后台地图（headless）**

| 步骤 | 做法 | 依据 |
|---|---|---|
| 保持系统运行 | `map.gameObject.SetActive(true)`，但**不调用** `WorldMap.Activate()` | `Activate` 会改 `UIState` 并禁用两台游戏相机（159697-159699） |
| 只关画面 | 关掉地图相机 `WorldMapCameraController.Camera.enabled=false` + 地图画布 `UIManager.WorldMapCanvas` | 演示层与逻辑层分离 |
| 解除阻挡 | `map.RemoveMovementBlocker(map)` | `Close()` 会加阻挡（159742），`IsTownMovementBlocked` 会挡输入（163926） |
| 同步初始位姿 | `map.Townheart.Teleport(world.TownheartWorldPosition, world.TownheartRotation)` | 避免 `OnEnable` 回吸到过期的地图位置（163914） |
| 注入输入 | Harmony postfix `FlotsamInputManager.GetMovementInput`（107211，**唯一调用者**是地图移动器 164002） | 保留引擎能耗/冷却/物理的权威性 |
| 节流提交 | 每 `commitInterval`（默认 0.15s）用**真实的连续帧位姿**派发一次 `DispatchTownheartMove` | 重生成/寻路/warp 从"每物理帧"降到 ~6.7 次/秒 |
| 地图键交接 | Harmony prefix `WorldMap.Close`：处于后台模式时先退出并 `return false` | `WorldMapManager.Update` 随即调用 `OpenMap()`（162426-162428），原版 `Activate()` 才能正确播种 `_startPosition` |

### 6.2 建筑查找：全挤在一起、未用原生分类、按钮不能记忆位置

**根因**：分类与页签在 `OnEnable` 里构建，而 `OnEnable` 发生在 **BepInEx 启动阶段**——那时还没有任何场景，`GameManager.Instance` 与 `GameManager.Settings` 都是 `null`，所以 `GameBuildings.Categories()` 返回**空列表**，只剩一个"全部"页签 → 整张表平铺。

**v2**：分类改为**懒加载**（`OnGameStart` 与首次打开面板时），并按原生方式呈现——分类**图标** `BuildableCategory.IconSprite`（56390）、分类**配色** `BuildableCategory.UIColor`（56394）、每类数量；行内用 `Properties.Icon` + `buildable.Name` + 原生故障数（`PopulateMalfunctions` 17065）；"全部"视图按分类分组带彩色表头；排序用游戏自己的 `SortBuildableList`（142434）。HUD 按钮与窗口位置可拖拽并写入 `config.json`（框架层给 `IHudButton` 增加了 `Position`/`Draggable`/`Moved`）。

### 6.3 材料辅助：缺料行点不到

**根因**（代码证据）：缺料提示是**跟随鼠标的悬浮框**——`TooltipPanel.Update`（82064-82074）每帧把浮层重定位到光标处，偏移 `(15,5)`（82011/82316-82341），离开触发区立刻隐藏（82418-82433 → 82205 `SetActive(false)`）；而每个 `RecipeItemDisplay` 在 `Awake` 里都被挂了 `ItemTooltip`（81729-81747/70949-70953）。所以鼠标一靠近就出现、一移开就消失，**行本身拿不到点击**。而我上一版的 `→生产` 标记还是 `raycastTarget=false`（不接收点击），固定 56×20 还可能溢出到行外。

另外，**不能用故障/警告图标当触发**：`Recipe.AddMallfunction` 仅在"该配方队列为空"时才挂上（24667），且每次排产尝试都会先 `ClearMalfunctions()`（25375）再重加（25398-25399）——它是闪烁的。

**v2**：挂在**常驻可点的东西**上——
- Harmony postfix `ProductionPanelRecipeToggle.Initialize`（77050）幂等附加组件；
- postfix `UpdateState`（77072）同步；因故障信号不稳定，另加 0.5s 轮询兜底；
- 按钮是**真 Button**、`Image.raycastTarget=true`、矩形**收在配方行内部**（右侧内缩 2px），所以它在自己的矩形内赢得射线，行其余部分仍是原版的选择行为（`onValueChanged` → 69582 → 69527 → `SetSelectedRecipe` 25098）；
- 另加**快捷键 `G`**：直接作用于当前打开的生产者面板（`BuildablePanel.Buildable` → `TryReturnBuildableExtendable<Producer>`），完全不依赖任何悬停 UI；
- 缺料判定与游戏自己一致：`Community.PlayerCommunity.Inventory.ReturnCount(ing) < ing.Amount`（70844）。

### 6.4 小地图：分不清东西、想要原生展示

**为什么不能直接复用原生地图**（v2 recon 结论）：`WorldMap.AddWorldTile`（159830）实例化瓦片时用的是 **prefab 的 parent**，不是 `WorldMap` 本身；地图关闭后这些对象虽然存活（`PruneWorldtiles` 159854 只销毁离开 `World.Tiles` 的），但它们位于**被停用的父级**之下——单独 `SetActive(true)` **不渲染任何东西**；而整棵重新激活又会连带它的移动器在暂停时驱动全局 `Physics2D.Simulate`（163952-163958）。Route A（第二相机）受制于场景序列化的 `cullingMask`/URP 2D 相机堆叠（全文件只有一处 cullingMask 运算，165593），不可验证。

**v2 做法：用游戏自己的资源合成**
- **底图**：真实迷雾遮罩 `WorldTile.FogOfWarAlphas`（157522，公开 `byte[]`，逐顶点 alpha 来自 161757-161770，索引 `v = j + i*(Cells+1)`）叠加瓦片海域轮廓；
- **标记**：`ISpawner.Icon`（139243）——**接口成员是公开的**（只有地标的后备字段 `_uiIcon` 是 internal），所以能直接拿到地标/兴趣点/漂浮垃圾的**原生图标**；
- 图标用**池化的 UGUI Image** 画在贴图之上：任意缩放下都清晰，也不需要 `Sprite.texture` 可读（避免图集不可读的坑）；
- 未侦察的图标按 `ScoutingState` 半透明；底部图例给出各类数量；镇心用程序生成的箭头显示朝向。
- `fogInvert` 配置：代码无法判定"1=雾"还是"1=可见"，用配置兜底。

### 6.5 顺带修掉的框架问题

冒烟验证发现材料辅助整个 mod 加载失败：`AccessTools.Method(typeof(ProductionPanelRecipeToggle), "Initialize")` 抛 **`AmbiguousMatchException`**（Harmony 会连带搜索基类，`Initialize` 有多个匹配）——而这个异常发生在 `PatchService` 之外，于是 `OnEnable` 整体抛出，mod 被标记为失败。已新增 **`GamePatches`**（`DeclaredOnly` 精确重载查找 / 唯一匹配才返回 / 永不抛出 / 失败时 `Describe()` 列出候选），并在两个打补丁的 mod 中改用它，同时把补丁段落逐条 try/catch，使单个目标失败只降级不致命。

## 附录 C：未验证项与验证清单

**未验证（不要在实现时当成既成事实）**

1. **Nexus 7 个 mod 的实际加载器**（BepInEx / UMM）——页面被人机验证拦截。→ 你去看 Requirements 页即可确认。
2. **Unity 6000.3.16f1 上 BepInEx 5.4.23.5 的实际可用性**——该版本含"Unity 6"修复，但 6000.3 更新；必须冒烟测试（见 M0）。
3. **场景/prefab 层级**：`WorldMapTownheartPhycis2D` 是否为 `WorldMap` 的子物体（依据是 159532 的序列化引用与 159687 的接线）——反编译产物里没有 `.unity/.prefab`，需在 Unity 资产层确认。
4. **四个 `RewiredAction` 上序列化的 action id 是否就是 69-72**（机制已确定，具体数值是场景数据）。`RewiredActionInfoBar` 恰好在 159761 注册 Forward/Backward/RotateLeft/RotateRight，与此高度一致。
5. **移动器的 `_mode` 在实机场景中是 `MoveTo` 还是 `Velocity/Force`**（`[SerializeField]`，163837）——影响我们是走 `MovePosition` 还是 `SetVelocity`。
6. **`UIManager.Initialize()` 二次调用的安全性**（重复事件订阅 + `_previousUIStates` 再入栈，111331-111336）——因此 v1 用独立 Overlay。
7. **`BuildableOverviewListItem`/`BuildableOverviewCategory` 的 prefab 能否在运行时被 mod 取到**——无 `Resources.Load` 路径，倾向"不能"，故自建行。
8. **是否存在其它在"地图关闭"时调用 `World.RepositionTownheart` 的代码路径**（如剧本地标转场 160293/160303）——若有，需做互斥。
